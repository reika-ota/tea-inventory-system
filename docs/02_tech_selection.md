## 1. 選定方針

- 無料のサービスのみで構築・運用できること（NFR-01）
- 家族のみアクセス可能かつ毎回の認証操作が不要であること（NFR-02, 03）
- スマートフォンで快適に使えること（NFR-04）
- 整合性（排他制御・楽観ロック・冪等性・履歴）の仕組みを自前で実装し、学習できること（NFR-06〜09、学習目的）
- データをスプレッドシートで直接確認・バックアップできること

## 2. システム構成の比較

| 観点 | A案：GitHub Pages＋GAS（API）＋スプレッドシート＋Googleログイン | B案：GAS完結（HtmlService）＋スプレッドシート | C案：Firebase（Hosting＋Auth＋Firestore） |
|---|---|---|---|
| コスト | 無料 | 無料 | 無料枠内 |
| アクセス制御 | IDトークンをGASで検証し、許可メールアドレスと照合 | スプレッドシート共有＋「アクセスしているユーザーとして実行」 | Firebase Auth＋セキュリティルール |
| スマホでの使い勝手 | ◎ 通常のWebアプリとして動作、ホーム画面追加可 | △ iframe内表示、Googleのバナー表示 | ◎ |
| 整合性の実装 | LockService等で自前実装（学習効果大） | 同左 | トランザクション標準搭載 |
| データの直接確認 | ◎ スプレッドシート | ◎ スプレッドシート | △ 管理コンソール |
| 構築の手間 | 中（OAuthクライアント作成、CORS対応） | 小 | 中 |
| 学習効果 | ◎ 認証・API・整合性を一通り経験 | △ | ○ |

### 決定：A案

要件をすべて満たし、スマートフォンでの使い勝手が良く、整合性の仕組みを自前で実装できるため。

## 3. 採用技術一覧

| 層 | 採用技術 | 選定理由 |
|---|---|---|
| 言語 | TypeScript（フロント・GAS共通） | API型定義とドメインロジックを共有し、仕様のずれをコンパイル時に検出するため |
| フロントエンド | React＋Vite | 業務で採用されている技術であり、学習成果を業務に活かせるため |
| UIライブラリ | MUI | 部品が揃っており、画面を手早く作れるため |
| アイコン | Material Icons（@mui/icons-material） | MUIと統一するため。原則としてこれを使用し、適切なものがない場合のみ独自に作成する |
| ルーティング | React Router（HashRouter） | スマホの「戻る」操作に対応するため。GitHub Pagesでの再読み込み時の404を避けるためハッシュ方式とする |
| サーバー状態管理 | TanStack Query | 取得データのキャッシュ、更新後の再取得、楽観的更新と失敗時の巻き戻しを標準機能で実現するため |
| ホスティング | GitHub Pages | 無料。GitHub Actionsでビルド・デプロイを自動化する |
| API | Google Apps Script（Webアプリとしてデプロイ） | 無料。スプレッドシートとの親和性が高い |
| データストア | Google スプレッドシート | 無料。データを直接確認・修正・バックアップできる |
| 認証 | Google Identity Services（Googleログイン） | 初回ログイン後は自動ログインが可能（NFR-03） |
| GAS開発環境 | clasp 3系＋バンドラー（Vite／Rollup） | ローカル開発・Git管理のため。clasp 3系はTypeScriptを変換しないため、バンドラーでJSに変換してからpushする |
| 単体テスト | Vitest | Viteと統合でき、フロント・shared双方で使える |
| 静的解析・整形 | ESLint＋Prettier | コード品質の統一 |
| パッケージ管理 | npm | 標準 |
| CI/CD | GitHub Actions | 無料枠内でフロントのビルド・デプロイ、テスト実行 |
| 開発支援 | Claude Code | 開発フェーズ以降の実装支援 |

## 4. リポジトリ構成

```
tea-inventory/
├── docs/        設計書（要件定義〜テスト）
├── frontend/    React＋Vite（GitHub Pagesへデプロイ）
├── gas/         GAS API（バンドル後 clasp push）
├── shared/      API型定義・ドメインロジック（フロント・GAS双方から参照）
└── CLAUDE.md    Claude Code向けプロジェクト説明
```

### 4.1 設計方針
- 在庫引当（先期限先出し）、残り回数計算、バリデーション等のドメインロジックは `shared/` に純粋関数として実装し、GAS固有API（SpreadsheetApp, LockService 等）に依存させない
- これによりドメインロジックをローカルでVitestにより単体テストできる

## 5. 制約・注意事項

| No | 内容 | 対応方針 |
|---|---|---|
| 1 | GitHub Freeでは、Pagesを使うリポジトリは公開（public）にする必要がある | 秘密情報をリポジトリに置かない。OAuthクライアントID・GASのURLは公開されても問題ない情報であり、保護はGAS側のトークン検証で担保する |
| 2 | GASはOPTIONS（プリフライト）リクエストに応答できない | POSTは `Content-Type: text/plain` で送信し、本文をJSONとして扱う |
| 3 | GASの応答は1〜2秒程度かかることがある | 更新操作は楽観的UI（先に画面反映、失敗時に巻き戻し）とする |
| 4 | スプレッドシートにはトランザクションがない | LockServiceによる排他、楽観ロック（版番号）、操作IDによる冪等性チェックで担保する |
| 5 | GASには実行時間・呼び出し回数等の割り当て上限がある | 家族数名の利用では問題にならない想定。基本設計で読み書き回数を最小化する |
| 6 | Googleログインのトークン（IDトークン）は約1時間で失効する | Google Identity Servicesの自動ログインで再取得する |

## 6. 学習方針（React）

React未経験のため、以下の範囲から始め、必要になったものだけ追加する。

- 関数コンポーネントとフック（useState, useEffect, useReducer）を基本とする
- グローバル状態管理ライブラリ（Redux等）は採用しない（サーバーから取得したデータはTanStack Queryで管理する）
